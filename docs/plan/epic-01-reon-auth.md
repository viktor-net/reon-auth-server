## Цель эпика

Построить подсистему ИБ платформы ИС РЕОН 2.0: единая аутентификация всех
модулей и административного фронтенда через общий Keycloak на DEV-стенде и
собственная авторизация (иерархический RBAC и ABAC) с чётким стандартом
подключения сервисов. Проверяемый итог эпика: любой новый модуль подключает
аутентификацию и базовую авторизацию по стандарту за часы, а не за недели,
без собственной логики входа и без ручной фильтрации тенантов.

## Контекст и источники

- ADR 04.01.04 «Выбор архитектуры авторизации (Иерархический RBAC и ABAC на
  базе Keycloak и Spring Security)», статус «Предложено» — PDF «Выбор
  архитектуры.pdf» и дубль «дополнительно авторизация.pdf». Решения ADR
  приняты за основу семантики: орг-дерево в группах IdP, capabilities-роли на
  группах, неизменяемый `org_id` как ABAC-якорь, Master Admin short-circuit,
  проверка `jwt.org_id == resource.org_id` и родительство пути группы.
- Диаграммы «Аутентификация DEV.pdf», «тоже АутентификацияDEV.pdf»: OIDC
  Authorization Code, reverse proxy перед IdP на DEV/TEST (страницы обрезаны,
  поток восстановлен по видимой части).
- Решения пользователя от 2026-11-01 (journal local-20261101-01):
  своего кода аутентификации не пишем — настраиваем Keycloak; Keycloak общий
  для всех модулей и админ-фронтенда; Angular-админка сейчас ходит в Keycloak
  напрямую через Code с PKCE (временная dev-схема); BFF отложен; СУДИР не
  заменяет Keycloak, в СУДИР только аутентификация своих пользователей, плюс
  формовая аутентификация в Keycloak; детальную авторизацию строим свою,
  сейчас обходимся ролями и claims; кода приложений в репозитории пока нет.
- ADR написан для Spring; его семантика не зависит от стека и перенесена без
  привязки к языку.

## Целевая архитектура (композитно)

```
[Пользователь]
   │ форма / SSO СУДИР (будущее)
   ▼
[nginx :8090] ── reverse proxy, лимиты заголовков ≥32k
   ▼
[Keycloak realm=reon] ── IdP: формовый вход, OIDC (code с PKCE, client_credentials),
   │                      орг-дерево группами, capabilities-роли на группах,
   │                      атрибут org_id, JWT: realm_access.roles, groups, org_id
   ├─► [Angular-админка] ── public client reon-admin-web, Code с PKCE напрямую (DEV, временно)
   ├─► [backend-модули]  ── bearer JWT, aud=reon-api, валидация и enforcement в процессе
   └─► [сервис→сервис]   ── reon-service, client_credentials
[Проверка прав] ── в приложении: 3 шага (MASTER_ADMIN → capability →
   │                 org_id и иерархия), фильтрация выборок по org_id
[Реестр орг-структуры] ── org_id как master data, синхронизация с группами
   │                 Keycloak (задача 04; заменяет ручные атрибуты и DEV-зеркало org_id на пользователях)
[СУДИР] ── внешний источник аутентификации своих пользователей, identity
            brokering (задача 05, ждём контракт)
[BFF] ── серверный обмен кода для web-клиентов (задача 06, отложен решением)
[PDP детальных правил] ── реестр политик слоёв/объектов/операций (задача 07,
            правила появятся отдельно)
```

## Принципы

1. Не строить собственный IdP: аутентификация — Keycloak (и СУДИР как
   федеративный источник), своё пишем только там, где Keycloak не достаёт до
   данных: enforcement, реестр орг-структуры, политики.
2. Авторизация грубого уровня (роли, org_id) проверяется в процессе модуля по
   claims JWT без сетевых вызовов (решение ADR, альтернатива 1); детальные
   правила — централизованно (задача 07), когда появятся.
3. DEV-схемы помечаем как временные: прямой ход SPA в Keycloak, ROPC для
   smoke, DEV-зеркало org_id на пользователях. Продуктовые схемы — в задаче 08.
4. Всё воспроизводимо из чистого клона (CONTRIBUTIONS.md): публичные образы,
   закреплённые теги, секреты только dev-образца.
5. Контракты (claims, клиенты, порты) фиксируются в brief и стандарте;
   меняются только через brief.v2 и журнал.
