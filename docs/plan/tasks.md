## Задача 01 — DEV-стенд: общий Keycloak, nginx, realm как код и smoke

- Подробно: `docs/plan/tasks/01-dev-stand.md`

- **task-id:** `local-20261101-01`, size **M**, **закрыта** (reduce и close в журнале).
- **Цель:** поднять воспроизводимый из чистого клона DEV-стенд единой
  аутентификации, который используют все модули и административный фронтенд:
  Postgres, Keycloak 26.5.5 и nginx, realm и dev-данные описаны кодом.
- **Что сделано:** `docker-compose.yml` (nginx 8090, Keycloak 8084,
  Postgres 5434); realm `reon` и dev-пользователи через `keycloak-config-cli`
  (one-shot `reon-auth-keycloak-init`, идемпотентен); клиенты `reon-admin-web`
  (public, Code с PKCE S256), `reon-api` (аудитория), `reon-service`
  (client_credentials), `reon-dev-smoke` (ROPC, DEV-only); группы орг-дерева
  и capabilities-роли; `org_id` атрибутом через штатный
  `oidc-usermodel-attribute-mapper`; smoke на bash и pwsh — по 52 проверки,
  0 FAIL.
- **Критерии приёмки:** стенд поднимается `docker compose up -d` из чистого
  клона; init идемпотентен; оба smoke зелёные; секретов в репозитории нет.
- **Итог:** принято reviewer-2 с рисками; отклонения (attribute-mapper вместо
  скрипт-маппера, `MASTER_ADMIN` на `/reon/admins`) ратифицированы в
  `reduce.md`.
- **Что осталось как долг:** ROPC, `/admin/` через nginx, DEV-зеркало
  `org_id` на пользователях — уборка в задаче 08 (и 04).

## Задача 04 — Реестр орг-структуры и синхронизация с Keycloak

- Подробно: `docs/plan/tasks/04-org-registry.md`

- **task-id:** `local-20261101-04`, size **M**, готова к захвату после 03.
- **Цель:** заменить ручные атрибуты групп в `realm.yml` управляемым реестром:
  сущность `OrgUnit` (дерево, неизменяемый `org_id`), EF-модель и миграции
  Postgres, admin API орг-дерева и воркер синхронизации групп и атрибутов
  Keycloak с реестром.
- **Проверяемо:** после изменения дерева через API группы и атрибуты Keycloak
  сходятся с реестром; `org_id` ранее выданных привязок не меняется при
  переименованиях; синк идемпотентен (converge-тест).
- **Не входит:** UI управления деревом (только API и curl); делегирование
  доступа между тенантами (правила — задача 07); миграция исторических данных
  (данных пока нет).
- **Файлы:** `src/Reon.Core/**`, `src/Reon.Infrastructure/**` (EF, миграции,
  Keycloak-синк), `src/Reon.Api/**` (admin endpoints),
  `tests/Reon.Infrastructure.Tests/**`.
  применяются к чистому Postgres (Testcontainers); converge-тест и
  идемпотентность; переименование сохраняет `org_id`; CRUD и curl-примеры.
- **Ограничения:** индекс по `org_id` во всех ресурсных таблицах; сервисный
  аккаунт `reon-service` с ограниченными ролями realm-management, не global
  admin; синк не удаляет группы с живыми пользователями без явного флага.
- **Риски:** гонка синка с ручными правками в админке Keycloak; слишком
  широкие admin-права сервисного аккаунта.
- **Открытый вопрос:** БД реестра — по умолчанию отдельная схема `reon_auth`
  в Postgres стенда.

## Задача 05 — Интеграция СУДИР (identity brokering)

- Подробно: `docs/plan/tasks/05-sudir-brokering.md`

- **task-id:** `local-20261101-05`, size **M**, **блокирована**: нет контракта
  СУДИР (протокол, endpoints, состав пользователей).
- **Цель:** подключить СУДИР как федеративный источник аутентификации СВОИХ
  пользователей к общему Keycloak: identity brokering (OIDC или SAML — по
  факту контракта), маппинг субъектов СУДИР в группы и роли realm `reon`,
  сохранение формового входа для локальных пользователей.
- **Проверяемо:** вход через кнопку СУДИР на DEV даёт JWT с теми же claims
  (`roles`, `groups`, `org_id`), что и формовой вход того же субъекта; оба
  входа покрыты smoke; init остаётся идемпотентным.
- **Не входит:** авторизация в СУДИР (СУДИР даёт только аутентификацию);
  синхронизация каталога пользователей СУДИР (по умолчанию just-in-time
  маппинг); замена формового входа (обе схемы сосуществуют).
- **Файлы:** `docker/keycloak/realm.yml` (broker), `docker/keycloak/sudir/*`,
  `docs/standards/service-auth.md` (раздел СУДИР — правит scribe),
  `scripts/smoke-auth.sh` (сценарий federated login).
- **Ограничения:** секреты клиента СУДИР — только через окружение, не в
  `realm.yml`; тесты без реального СУДИР — mock-OIDC IdP контейнером (второй
  realm Keycloak как стенд-дублёр).
- **Риски:** контракт неизвестен (потребуется `brief.v2`); маппинг
  орг-принадлежности может потребовать реестр (04) раньше срока.

## Задача 07 — Детальные правила доступа: реестр политик и PDP

- Подробно: `docs/plan/tasks/07-detailed-policies.md`

- **task-id:** `local-20261101-07`, size **L**, **блокирована**: правила
  доступа к слоям, объектам и операциям ещё не сформулированы владельцами
  продукта.
- **Цель:** дать детальным правилам место и интерфейс: реестр политик
  (субъект → действие → ресурс → условие, декларативно, в читаемом формате) и
  PDP-endpoint оценки для модулей, которым грубых claims недостаточно. Грубая
  авторизация остаётся внутри приложения (библиотека 03); PDP — только для детальных
  правил, с кэшем решений на стороне модуля.
- **Проверяемо:** набор правил из примера продукта даёт ожидаемые allow/deny
  в интеграционных тестах; `MASTER_ADMIN` short-circuit сохранён и на PDP.
- **Не входит:** перенос грубой авторизации в PDP; UI редактора политик
  (только API и файлы-декларации); ReBAC-граф (отклонён в ADR).
- **Файлы:** `src/Reon.Core/**` (модель политик),
  `src/Reon.Infrastructure/**` (хранение), `src/Reon.Api/**` (`POST
  /authorize/evaluate`, admin API политик), `tests/**`.
- **Контракт evaluate:** `{ subject, action, resource, context } →
  { allow, reason, policyVersion }`; политики версионируются для аудита.
  примера продукта проходят e2e через PDP; кэш в библиотеке 03
  инвалидируется по `policyVersion`; журнал оценок пишется в формате,
  согласованном с задачей 08.
- **Риски:** модель политик может не угадать форму правил — начинать с 5-10
  реальных примеров, полученных до старта кода.
- **Открытый вопрос:** форма правил (Rego-подобная/YAML/своя) — по примерам
  продукта.

## Задача 08 — Продуктовые практики и hardening

- **task-id:** `local-20261101-08`, size **M**, стартует последней, по
  готовности 03-07.
- **Цель:** убрать dev-временные решения и подготовить продуктовые практики:
