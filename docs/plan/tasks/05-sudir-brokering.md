# Задача 05 — Интеграция СУДИР (identity brokering)

- task-id: `local-20261101-05`
- size: **M**
- статус: **блокирована** внешним контрактом СУДИР
- зависимости: 01 (стенд); внешний вход — протокол, endpoints и состав
  пользователей СУДИР
- доска: `.agents/tasks/local-20261101-05/`
- модели: все роли — `opencode/deepseek-v4.1-flash` (Zen)

## Зачем

Часть пользователей платформы аутентифицируется в СУДИР. Решение владельца:
СУДИР **не заменяет** Keycloak — он остаётся источником аутентификации своих
пользователей, а Keycloak подключает его как федеративный IdP. Формовая
аутентификация Keycloak сохраняется для остальных.

Итог: пользователь СУДИР входит через кнопку на странице входа Keycloak и
получает тот же контракт JWT (`realm_access.roles`, `groups`, `org_id`), что и
при формовом входе. Модули не знают, откуда пришёл пользователь.

## Что входит

1. **Broker в Keycloak.** Identity provider в realm `reon` (OIDC или SAML — по
   факту контракта), маппинг субъектов СУДИР в пользователей realm.
2. **Маппинг прав.** Правила, по которым атрибуты СУДИР превращаются в
   группы орг-дерева и capabilities-роли: таблица соответствия либо claim от
   СУДИР. Решение принимается по контракту, фиксируется в `brief.v2`.
3. **Сосуществование входов.** Кнопка СУДИР на странице входа; формовой вход
   не сломан; smoke покрывает оба сценария.
4. **Секреты.** Клиентские секреты СУДИР — только через окружение стенда, не
   в `realm.yml`.
5. **Тесты без реального СУДИР.** Mock-OIDC провайдер контейнером (например,
   второй realm Keycloak как стенд-дублёр СУДИР): вход, claims, отказ.

## Что не входит

- Авторизация в СУДИР: он даёт только аутентификацию.
- Синхронизация каталога пользователей СУДИР в Keycloak: по умолчанию
  just-in-time маппинг при входе.
- Замена формового входа: обе схемы живут параллельно.
- Детальные правила доступа (07).

## Критерии приёмки

- [ ] Broker включён, кнопка на странице входа, формовой вход работает.
- [ ] JWT после federated login содержит контрактные claims.
- [ ] Smoke покрывает оба входа; вывод в result.
- [ ] Идемпотентность `keycloak-config-cli` сохранена.
- [ ] Секретов в репозитории нет.

## Риски

- **Контракт неизвестен**: brief уточняется через `brief.v2` после получения
  протокола, endpoints и состава пользователей.
- **Маппинг орг-принадлежности** может потребовать реестр (04) раньше срока:
  тогда задача 05 стартует после 04, а не параллельно.
- **Двойной источник идентичности**: один человек может существовать и в
  СУДИР, и локально — нужен явный порядок разрешения конфликта (по контракту).

## Открытые вопросы

- Протокол СУДИР (OIDC/SAML/кастомный) и endpoints — от владельца системы.
- Кто ведёт соответствие «пользователь СУДИР → орг-узел»: СУДИР в claim или
  таблица на нашей стороне.
- Нужна ли синхронизация каталога, если JIT-маппинга не хватит.
