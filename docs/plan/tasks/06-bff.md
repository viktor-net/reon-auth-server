- доска: `.agents/tasks/local-20261101-06/`

## Зачем

Сейчас Angular-админка ходит в Keycloak напрямую по Authorization Code с PKCE,
и токены живут в браузере. Для DEV это приемлемо и помечено как временное.
Продуктовая схема из диаграмм «Аутентификация DEV» — BFF: браузер общается
только с сервером приложения по сессионной куке, обмен кода на токены делает
сервер, токены не покидают сервер.

Пока BFF не нужен: единственный web-клиент — админка на DEV, а прямой ход
проще. Задача возвращается, когда появится требование «токенов в браузере
нет» или несколько web-клиентов с общим входом.

## Что входит

1. **BFF-слой.** Серверный endpoint `/auth/login` → редирект в Keycloak с
   `state` и `nonce`; `/auth/callback` → обмен кода (confidential client) на
   токены; `/auth/logout` → завершение сессии IdP и локальной сессии.
2. **Сессия.** Кука `HttpOnly`, `Secure`, `SameSite=Lax`, идентификатор
   сессии на сервере; хранение токенов серверное (в памяти или защищённом
   хранилище), без записи в браузер.
3. **Прокси API.** BFF передаёт запросы модулей с bearer-токеном из сессии;
   модули продолжают валидировать JWT по стандарту 02 и не знают о BFF.
4. **CSRF.** Защита для изменяющих запросов (double submit или
   синхронизирующий токен), проверка `Origin`.
5. **Конфигурация.** Новый confidential-клиент Keycloak (например
   `reon-web-bff`), секрет — только в секретах стенда; nginx проксирует BFF.
6. **Тесты.** e2e-сценарий входа/выхода в браузере (Playwright) с проверкой,
   что токенов нет ни в `localStorage`, ни в ответах браузеру.

## Что не входит

- Миграция Angular-админки на BFF: остаётся на прямой dev-схеме, пока
  владелец фронтенда не решит иначе.
- SPA без серверной части: им по-прежнему Code с PKCE напрямую.
- Мобильные клиенты.

## Критерии приёмки

- [ ] Браузерный e2e входа и выхода зелёный.
- [ ] Токены не видны клиенту (проверка по e2e-трассировке).
- [ ] CSRF-защита включена и покрыта тестом.
- [ ] Стандарт дополнен разделом про BFF (scribe).
- [ ] Сборка и тесты проекта зелёные.

## Риски

- **Двойная поддержка схем** (прямая SPA и BFF): стандарт должен чётко
  разводить их по типам клиентов, иначе фронтенд выберет «как проще».
- **Обрезанные диаграммы**: PDF неполные, поток восстановлен по видимой части;
  перед стартом нужны полные страницы (wiki pageId=36012151) или перерисовка
  схемы в `brief.v2`.
- **Секрет клиента**: BFF — confidential-клиент, секрет нельзя хранить в
  репозитории и нельзя отдавать браузеру.

## Открытые вопросы

- Полные диаграммы аутентификации — у владельца wiki.
- Нужна ли серверная сессия в Redis/БД или достаточно памяти процесса (влияет
  на горизонтальное масштабирование).
- Один BFF на все модули или BFF на модуль.
