# Задача 08 — Продуктовые практики и hardening

- task-id: `local-20261101-08`
- size: **M**
- статус: последняя в эпике; старт — по готовности 03-07
- зависимости: 03-07 по готовности
- доска: `.agents/tasks/local-20261101-08/`
- модели: все роли — `opencode/deepseek-v4.1-flash` (Zen)

## Зачем

DEV-стенд намеренно содержит послабления: ROPC у тестового клиента, прямой ход
SPA в Keycloak, `http` вместо TLS, `/admin/` через nginx, DEV-зеркало `org_id`
на пользователях, короткие времена жизни токенов. Каждое послабление удобно
для разработки и недопустимо в продукте.

Задача убирает послабления и фиксирует продуктовые практики, не ломая DEV.

## Что входит

1. **Профили стенда.** `docker-compose.yml` — DEV; отдельный prod-профиль
   (override-файл) с TLS-терминацией, продуктовыми TTL, отключёнными ROPC и
   scripts-фичей, закрытым `/admin/`.
2. **TLS и лимиты.** TLS на входном прокси, продуктовые лимиты заголовков и
   тела запроса на всех хопах (не только nginx стенда), проверка токеном
   ≥ 8 КБ.
3. **Времена жизни токенов.** Продуктовые значения access/refresh, политика
   logout и отзыва сессий.
4. **Уборка dev-решений.** ROPC выключен вне DEV; DEV-зеркало `org_id` на
   пользователях заменено механизмом из задачи 04; скрипт-маппер и
   `KC_FEATURES=scripts` не используются (уже так — зафиксировать).
5. **Аудит.** События входа, отказов авторизации и действий `MASTER_ADMIN`
   (short-circuit без аудита — известный риск задачи 03). Ротация без ручных
   действий.
6. **Индексы и производительность.** Индексы по `org_id` во всех ресурсных
   таблицах; проверка планов запросов на репрезентативных данных.
7. **Регламент обновлений Keycloak.** Версии образов, порядок обновления,
   проверка миграций realm, откат.
8. **CI.** Шаг прогона dev-only тестов со стендом; запрет ROPC вне DEV;
   проверка `git ls-files --eol` на смешанные окончания строк.

## Что не входит

- Пен-тест и внешний аудит безопасности: только внутренние проверки и
  конфигурация.
- HA-кластер Keycloak: оценивается отдельно при необходимости.
- Продуктовый реестр образов и registry: инфраструктурный вопрос вне эпика.

## Файлы

`docker-compose*.yml` (prod-профиль), `docker/nginx/**`, `docker/keycloak/**`,
`docs/standards/service-auth.md` (актуализация — scribe), `src/**` (аудит,
guard тенанта), `.github/**` или CI-конфиг проекта.

## Критерии приёмки

- [ ] Чек-лист hardening закрыт, по каждому пункту — вывод команды в result.
- [ ] DEV- и prod-профили разведены, оба воспроизводимы из чистого клона.
- [ ] ROPC и scripts-фича выключены в prod-профиле; проверено тестом.
- [ ] Аудит пишется, ротация не требует ручных действий.
- [ ] Индексы по `org_id` есть; план запроса проверен.
- [ ] Стандарт актуализирован scribe под продуктовые схемы.
- [ ] CI прогоняет dev-only тесты и проверку окончаний строк.

## Риски

- **Разведение профилей выявит непереносимость dev-допущений** (например,
  DEV-зеркало `org_id`): план замены из задачи 04 должен быть готов.
- **Fail-open EF-фильтра** (риск задачи 03): здесь добавляется guard или явное
  fail-closed поведение; после изменения тест-документ из 03 переписывается в
  негатив.
- **Смена TTL и отзыв сессий** — операция с внешним эффектом: только с
  подтверждением человека и записью в журнал (AGENTS.md §12).
