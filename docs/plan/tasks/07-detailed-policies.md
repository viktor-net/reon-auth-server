# Задача 07 — Детальные правила доступа: реестр политик и PDP

- task-id: `local-20261101-07`
- size: **L**
- статус: **блокирована** — правила доступа к слоям, объектам и операциям ещё
  не сформулированы владельцами продукта
- зависимости: 04 (реестр орг-структуры); внешний вход — примеры правил
- доска: `.agents/tasks/local-20261101-07/`
- модели: все роли — `opencode/deepseek-v4.1-flash` (Zen)

## Зачем

Грубая авторизация (роль и тенант) отвечает на вопрос «можно ли этому
пользователю этот тип операции в этом тенанте». Она не отвечает на «можно ли
ему этот конкретный объект»: черновик против опубликованного, свой филиал
против соседнего, операция над документом в статусе «на согласовании».

Детальные правила нужно где-то хранить, версионировать и оценивать
централизованно, иначе они расползутся по модулям в виде `if`-ов.

## Что входит

1. **Модель политик.** Декларативное правило: субъект (роль, группа, атрибут),
   действие, ресурс (тип и/или экземпляр), условие. Версионирование: у набора
   правил есть `policyVersion`, решения аудируются вместе с версией.
2. **Реестр.** Хранение политик (файлы-декларации в репозитории и/или таблица
   в Postgres), загрузка при старте, hot reload по версии.
3. **PDP-endpoint.** `POST /authorize/evaluate`: на входе
   `{ subject, action, resource, context }`, на выходе
   `{ allow, reason, policyVersion }`. `MASTER_ADMIN` short-circuit сохранён.
4. **Клиент в модулях.** Клиент PDP с кэшем решений,
   инвалидация по `policyVersion`; горячий путь грубой авторизации остаётся
   без сетевых вызовов.
5. **Аудит.** Журнал оценок: кто, что, с каким результатом, версия политик.
   Формат согласуется с задачей 08.
6. **Тесты.** Набор реальных правил продукта (5-10 примеров) проходит e2e через
   PDP; allow/deny совпадает с ожиданием; кэш не отдаёт устаревшее решение
   после смены версии.

## Что не входит

- Перенос грубой авторизации в PDP: проверка по claims внутри приложения остаётся (ADR).
- UI редактора политик: только API и файлы-декларации.
- ReBAC-граф (OpenFGA/Keto): отклонён в ADR.
- RLS Postgres как второй эшелон: вопрос задачи 08.

## Критерии приёмки

- [ ] Сборка и тесты проекта зелёные.
- [ ] Правила из примера продукта проходят e2e через PDP.
- [ ] Кэш в модуле инвалидируется по `policyVersion`.
- [ ] Журнал оценок пишется, формат согласован с задачей 08.
- [ ] `MASTER_ADMIN` short-circuit проверен тестом.

## Риски

- **Правил ещё нет**: модель может не угадать их форму. Мера — не начинать код
  без 5-10 реальных примеров от владельцев продукта.
- **Латентность**: PDP вызывается только при cache miss; SLA оценить
  нагрузочным тестом до приёмки.
- **Дублирование логики**: модули могут обойти PDP и написать свои проверки —
  чек-лист стандарта и ревью должны это ловить.

## Открытые вопросы

- Форма правил: Rego-подобная, YAML или собственная — решается по примерам.
- Где живут политики: только репозиторий (GitOps) или ещё и БД с админ-API.
- Кто владелец изменений политик и как выглядит согласование.
