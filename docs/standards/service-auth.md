# Стандарт подключения сервисов РЕОН к аутентификации и авторизации

- Версия: 1.0 (2026-11-01)
- Владелец: orchestrator/scribe `ses_e698f600cffeRs4u6jkQsJBWxL`
- Основание: ADR `docs/adr/0001-authn-authz-architecture.md`, контракт
  DEV-стенда из задачи local-20261101-01 (brief.v2, reduce), решения
  владельца продукта от 2026-11-01.
- Изменения стандарта — только через задачу доски с brief и reduce.

## 1. Область и термины

Стандарт обязателен для всех backend-модулей ИС РЕОН 2.0 и административного
фронтенда. Термины: IdP — Keycloak realm `reon`; RP — подключаемый сервис;
capability — роль формата `resource:action` (`report:read`); орг-узел — группа
Keycloak орг-дерева; тенант (организация) — владелец данных с неизменяемым
UUID `org_id`: орг-узлы одного тенанта (например `/reon/hq` и
`/reon/hq/finance`) несут один `org_id`, а иерархию внутри тенанта задают
пути групп; `org_id` — якорь тенанта для фильтрации данных.

DEV-стенд: issuer `http://localhost:8090/realms/reon` (nginx), админка Keycloak
`http://localhost:8084`. Запуск: `cp .env.example .env && docker compose up -d`;
проверка контракта: `bash scripts/smoke-auth.sh` или
`pwsh -File scripts/smoke-auth.ps1` (52 проверки, паритет).

## 2. Схемы подключения по типам клиентов

| Тип клиента | Схема | Клиент DEV-стенда | Статус |
|---|---|---|---|
| SPA/фронтенд (Angular-админка) | OIDC Authorization Code с PKCE S256 напрямую в Keycloak; токены живут в памяти вкладки, не в localStorage | `reon-admin-web` (public) | dev-схема, временная (решение владельца); продуктовая схема web-входа — BFF, задача 06 |
| Backend-модуль (API) | Bearer JWT: валидация подписи и claims в процессе, без сетевых вызовов к IdP на горячем пути | аудитория `reon-api` | продуктовая |
| Сервис→сервис | OAuth2 client_credentials; авторизация по `aud` и `azp` (allowlist сервисных клиентов), capabilities не применяются | `reon-service` | продуктовая |
| Web-приложение с серверной сессией | BFF: серверный обмен кода, кука-сессия, токены не покидают сервер | появится в задаче 06 | отложена |
| Smoke/интеграционные тесты стенда | ROPC (direct grants) | `reon-dev-smoke` | DEV-only; в продуктовых интеграциях запрещён |

Запрещено: свой код аутентификации (пароли, сессии входа) в модулях; ROPC вне
DEV; implicit flow; хранение токенов в localStorage/sessionStorage.

### 2.1. Инструкция подключения SPA (Angular-админка, dev-схема)

Библиотека OIDC RP — любая поддержанная командой фронтенда
(angular-auth-oidc-client, keycloak-js и аналоги); конфигурация обязательна
следующая:

| Параметр | Значение (DEV) |
|---|---|
| authority | `http://localhost:8090/realms/reon` |
| client_id | `reon-admin-web` (public, секрет не используется) |
| redirect_uri | `http://localhost:4200/` (второй экземпляр — `http://localhost:4201/`) |
| response_type | `code` |
| PKCE | обязателен, `S256`; не отключать |
| scope | `openid profile email` |
| post_logout_redirect_uri | `http://localhost:4200/*` |

- Токены хранить только в памяти вкладки; в localStorage/sessionStorage —
  запрещено (раздел 2).
- Refresh: в пределах сессионного окна 8 часов средствами библиотеки
  (silent renew); доступ короче — 900 секунд.
- Logout: `end_session_endpoint` с `post_logout_redirect_uri`; локальную
  сессию вкладки очищать до редиректа.
- Вызов API модулей: заголовок `Authorization: Bearer <access_token>`;
  аудитория `reon-api` уже в токене.
- Продуктовая схема web-входа — BFF (задача 06): прямой ход SPA помечен
  dev-only и не должен попадать в прод-конфигурации фронтенда.

## 3. Контракт JWT

| Claim | Тип | Содержание |
|---|---|---|
| `iss` | string | issuer realm; сверять строго |
| `aud` | string/array | содержит `reon-api` для пользовательских и сервисных токенов |
| `azp` | string | клиент, запросивший токен |
| `realm_access.roles` | array | capabilities и `MASTER_ADMIN` |
| `groups` | array | полные пути групп; организации — пути орг-дерева, кроме служебной `/reon/admins` |
| `org_id` | string | UUID тенанта пользователя |
| `sub`, `preferred_username` | string | субъект и логин |
| `exp`, `iat` | number | времена; DEV: access 900 c, refresh-окно 8 ч |

Примечание: `nbf` Keycloak может не выпускать — проверять только при
наличии. Лимиты заголовков задаёт хост модуля (раздел 4), продуктовые значения
и проверка на LB — задача 08.

Правила чтения claims:

- организация пользователя определяется по `org_id`, а не парсингом `groups`;
  `groups` нужны только для проверок иерархии (родительство пути);
- путь `/reon/admins` в `groups` — служебный (носитель `MASTER_ADMIN`): не
  считать организацией и не показывать в орг-структуре UI;
- сервисные токены не имеют `realm_access.roles` и `org_id` по дизайну:
  авторизуются по `aud` и `azp`; межсервисные операции от имени пользователя
  передают его токен, не сервисный.

## 4. Требования к валидации JWT (backend-модуль)

1. Подпись по JWKS issuer (`{issuer}/protocol/openid-connect/certs`),
   алгоритм только RS256; `alg=none` и HS* отклонять.
2. `iss` равен ожидаемому issuer строго (без суффиксов и слэш-вариаций).
3. `aud` содержит идентификатор аудитории модуля (для платформы — `reon-api`).
4. `exp`, `nbf` с допуском рассинхронизации часов не более 60 секунд.
5. Проверка отзыва не требуется (access короткоживущий); logout — на стороне
   клиента и сессии IdP.
6. Крупные токены: модуль и его прокси должны принимать заголовок
   Authorization до 32 КБ (nginx стенда настроен; настройки хоста модуля —
   раздел 6).
7. Валидатор не кэширует claims между запросами без проверки подписи.

## 5. Модель авторизации (три шага)

Порядок обязателен, короткое замыкание по шагам:

1. **Master Admin**: `realm_access.roles` содержит `MASTER_ADMIN` — доступ
   разрешён мимо проверок тенанта и иерархии (аудит события обязателен,
   появится в задаче 08).
2. **Capability**: требуется роль `resource:action` на операцию.
   Роли назначаются группам Keycloak, не пользователям.
3. **Контекст тенанта и иерархии**: `org_id` токена равен `org_id` ресурса,
   либо путь орг-группы токена является родителем пути орг-группы ресурса
   (наследование вниз по дереву). Фильтрация списков — EF-фильтром по
   `org_id` на уровне запроса, не пост-фильтрацией в коде.
   Тенант ресурса модуль берёт из своих master data (колонка `org_id`);
   путь орг-узла ресурса — из своих master data, а с готовностью реестра
   орг-структуры (задача 04) — из реестра. До задачи 04 ветка родительства
   применяется только к ресурсам, у которых путь узла есть в master data;
   иначе шаг 3 ограничивается сравнением `org_id`.
4. **Сервисные эндпоинты (без пользователя)**: авторизация по `aud` и `azp`
   через allowlist доверенных сервисных клиентов в конфигурации модуля
   (пример политики — раздел 6); capabilities и `org_id` не применяются.
   Операции от имени пользователя выполняются с пользовательским токеном,
   переданным вызывающим, а не с сервисным.

Детальные правила (слои/объекты/операции) появятся в задаче 07: реестр
политик и PDP-endpoint с кэшем по версии политик; до их появления модули
ограничиваются тремя шагами.

## 6. Реализация в модуле

Общего кода пока нет: каждый модуль реализует требования разделов 3-5 сам,
в своём стеке. Обязательный минимум:

- проверка подписи, issuer, audience и срока действия (раздел 4);
- разбор `realm_access.roles` в роли приложения, чтобы работали проверки
  capability;
- проверка трёх шагов (раздел 5) на эндпоинтах;
- фильтрация выборок по `org_id`;
- приём заголовка `Authorization` размером до 32 КБ на хосте модуля.

Общая реализация появится вместе с первым модулем: писать её раньше значит
угадывать чужие нужды. Этот стандарт — контракт, по которому она будет
сверяться.

## 7. Тестирование

- Mock-токены: локальная RSA-пара, свой JWKS-endpoint в тестовом хосте,
  claims собираются конструктором (роли, группы, `org_id`, aud); подпись
  валидатора направляется на тестовый JWKS.
- Обязательные негативные сценарии: просроченный токен; чужой `aud`;
  `alg=none`; отсутствующая capability; чужой `org_id` (404/403, не утечка
  существования ресурса); токен без `org_id`; сервисный токен против
  пользовательского эндпоинта.
- Интеграционные сценарии DEV: токены стенда через `reon-dev-smoke` (ROPC)
  помечаются dev-only и не ходят в CI продакшн-контуров.
- Паритет проверок: сценарии дублируются в smoke стенда, если меняют контракт
  (см. `scripts/smoke-auth.sh`).

## 8. Чек-лист подключения модуля

1. Клиент/аудитория согласованы с владельцем стандарта (новый модуль — новая
   задача доски: клиент в `realm.yml`, запись в разделе 2).
2. Валидация по разделу 4 реализована и покрыта тестами раздела 7.
3. Операции закрыты политиками capability; списки фильтруются по `org_id`.
   Фильтрация по `org_id` не заменяет проверку доступа: каждый эндпоинт с
   данными обязан быть закрыт политикой аутентификации и capability,
   иначе список останется открытым при отсутствии тенанта в токене.
4. Master Admin short-circuit и аудит согласованы с разделом 5.
5. Лимиты заголовков проверены нагрузочным токеном (≥ 8 КБ).
6. README модуля ссылается на этот стандарт и указывает свою аудиторию.
7. Smoke/интеграционные тесты модуля не требуют ROPC вне DEV.

## 9. CURL-примеры DEV (воспроизводятся smoke-скриптами)

```bash
# сервисный токен (client_credentials); aud проставляет audience-mapper,
# параметр audience не требуется
curl -s -X POST http://localhost:8090/realms/reon/protocol/openid-connect/token \
  -d grant_type=client_credentials \
  -d client_id=reon-service \
  -d client_secret=$REON_SERVICE_CLIENT_SECRET

# пользовательский токен (ROPC, DEV-only)
curl -s -X POST http://localhost:8090/realms/reon/protocol/openid-connect/token \
  -d grant_type=password \
  -d client_id=reon-dev-smoke \
  -d client_secret=$REON_DEV_SMOKE_CLIENT_SECRET \
  -d username=dev-finance -d password=dev-finance-pass

# discovery
curl -s http://localhost:8090/realms/reon/.well-known/openid-configuration
```

Значения секретов и паролей — dev-образцы из `.env.example` и
`docker/keycloak/dev-users.yml`; в репозитории только они.

## 10. Известные ограничения и временные решения

- Прямой ход SPA в Keycloak — dev-only (раздел 2); продуктовая web-схема — BFF
  (задача 06).
- `org_id` в DEV выдаётся из атрибута пользователя (зеркало атрибута группы):
  до задачи 04 не перемещать пользователей между орг-группами вручную.
- `/reon/admins` в `groups` — служебный путь (раздел 3).
- keycloak-config-cli не удаляет сущности, убранные из конфига: изменения «на
  удаление» на живом стенде — точечно через Admin API с записью в журнал
  задачи; оценка `IMPORT_MANAGED_*` — задача 08.
- Окончания строк репозитория приводятся к режиму CONTRIBUTIONS.md массовой
  правкой в задаче 03 вместе с `.editorconfig`/`.gitattributes`.
